## 2. 顶层约束：Beancount / fava 合规（可验证条款）

> **硬约束原文**：「对账户和交易的操作要符合 beancount/fava 的规则」；老板拍板「**不输出指令、对齐语义**」——导出的 `.beancount` 仍是纯普通交易，不引入 `balance`/`pad` 指令，不提前启动 M4 语法范围。
> 以下 C-01~C-06 为**主理人在项目 `.venv`（beancount 3.2.3）用 `bean-check` 实测结论**（`check-bean.sh` 自检通过、`BEAN_CHECK_STRICT=1 go test ./internal/export/... ./internal/beancount/...` 全绿），本 PRD 转为可验证条款；C-07 为项目既有铁律。

| 编号 | 实测结论 | 本版必须遵守的可验证条款 | 影响需求 |
|---|---|---|---|
| **C-01** | **`balance` 是日初断言**：`D 日 balance 100.00` + 当日 -20 交易 → 通过；断言 80.00 → `expected 80 != accumulated 100`。即校验截至 **D 日初（前一日日终）**，**不含当日交易** | 「截至指定日期余额」的累计口径 = `date < D` 的全部 posting 之和；**不含 D 当日**；自动平衡分录必须落在 D 之前 —— **【主理人裁定 2】落账日期默认 `D-1`，且必须 `>= max(账户 open_date, 账本期初日期)`；区间为空（D 太早）返回可读错误，不得静默取更早日期**。依据：`open` 晚于首笔交易报 `Invalid reference to inactive account`（C-04）、pad 日期必须早于 balance 日期（C-02 同日写报 `Unused Pad entry`）。UI 文案统一「截至 D 日初（前一日日终）」 | #3 |
| **C-02** | **`pad` 必须与更晚日期的 `balance` 配对**；同日写报 `Unused Pad entry` + 断言失败。Beancount 自己把 pad 物化成普通交易：flag `P`、日期 = pad 日、对手科目 = pad 第二参数、金额 = `balance 目标值 − 截至断言日初累计`（同文件已有 30 时差额自动变 70） | `target=new` 展开 pad 时按此语义计算差额，但**输出为普通 `*` 交易**（不输出 `P` flag 指令形态、不输出 `pad`/`balance` 指令）；差额按「目标值 − 截至断言日初累计」算，不照搬目标值 | #6 |
| **C-03** | **账户名规则**：根必须五类之一且大写开头；**根后第一段必须 ASCII 大写 / 数字开头**——`Expenses:餐饮` 报 `Invalid account name`，但 `Expenses:Food:早饭` 通过（第三段起允许中文）；小写段、空格段失败 | 新建 / 增加下级的 `name` 必须过格式校验（根 + 首段规则）；**延续 `name`（ASCII 合法）与 `display_name`（中文展示）分离**（seed 正确做法见 `internal/seed/accounts.go:27-70`）；不合法输入 400 且给出可读原因，不得落库后再导出失败 | #2（P0） |
| **C-04** | 未 open 就引用 → `Invalid reference to unknown account`；open 晚于首笔交易 → `Invalid reference to inactive account`；**close 后再 open 同名 → `Duplicate open directive`** | 账户 open_date 不得晚于其首笔交易；关闭后不可重建同名；**`internal/export/beancount.go:217-218` 注释写「支持 close 后再 open 同名」是说反了**，须在 S0 修正（CHANGELOG 0.4-A 结论正确） | #2 / #6 / S0 |
| **C-05** | **合并到当前账本时不能照搬断言**（实测）：当前账本 500 + 外部文件 `pad`/`balance 100` → 自动生成 **-400** 的 `P` 交易把现有余额拉到外部值；单独 `balance 30` 无 pad → `Balance failed: expected 30 != accumulated 500` | `target=current` 遇 `pad`/`balance` **默认整体拒绝**（不物化、不改余额）；预检必须展示按当前账本重算的差额让用户看见后果 | #6 |
| **C-06** | fava 是文本编辑器、允许原地改源文件历史交易，但项目是 **append-only + 离线同步**（uuid 身份键、水位、幂等哈希），**不能照搬**；Beancount 官方「纠错靠新增指令」原则反而强化路径 B | 交易修改不得原地改；必须新增记录表达纠错；不得新增同步 op 或改变离线协议版本 | #5 |
| **C-07** | 项目既有铁律（`AGENTS.md` §1 L31、§8 L219-220） | 导出 `.beancount` 必须被 `bean-check` 直接校验通过（退出码 0、无报错）；金额一律定点十进制字符串 / 整数最小单位，**禁浮点**；同一 transaction 下按 commodity 分组的 `postings.amount` 之和必须为 0 | 全部 |

**约束边界说明（【主理人裁定 3】采纳，架构师按此设计，不改变口径）**：C-02 的 `target=new` 支持属于 **输入侧** 展开为普通交易、**不输出** 指令、**不落库** 断言，因此与 D-02「不提前启动 M4 语法范围」**不冲突**；**M4 范围指的是「输出 `balance`/`pad` 指令 + 未知指令原样保留 + 全语法导入到当前账本」**。据此：
- `target=new` 的 pad 物化用**普通 `*` 交易**（**不使用 Beancount 原生 `P` flag**，即 Q-09 结论），断言转为**导入后自检**、不落库、不导出；
- **不收窄 D-11**：`target=current` 仍默认整体拒绝 `pad`/`balance` 并给指引，`target=new` 仍可完整支持；
- 导出的 `.beancount` 始终是纯普通交易，符合「不输出指令、对齐语义」硬约束。

## 5. 逐条功能规格与验收标准

> **通用门禁（六条全部适用，不逐条重复）**：见 §6。
> **稳定错误码**：统一响应 `{error, code?, ...details}`（`AGENTS.md` §7 L213），前端错误码到中文文案映射集中一处，不把 HTTP 500 原文甩给用户。

### 5.0 关键流程与状态流转

**流程 A · 账本删除**

```
owner 打开账本页 → 读 member_count（除 owner 外成员数）
  ├─ >0 → 删除入口禁用 + 提示「还有 N 位成员，需先移除」；后端 DELETE 409 ledger_has_members
  └─ =0 → 弹确认（输入账本名）+ 展示账户数/交易数
            → 先判是否该用户最后一个账本 → 是 → 409 last_ledger
            → 生成 trigger=pre-ledger-delete 一致性快照（VACUUM INTO，禁复制 db 文件）
            → 单一事务软删 ledgers.deleted_at + 写审计
            → GET /api/ledgers 不再返回；session.refreshLedgers 兜底切到最小有效账本
```

**流程 B · 余额校准（日初语义）**

```
owner/editor 打开账户详情 → 填 {as_of_date: D, targets: [{commodity, target_balance(带符号)}]}
  → 预检：当前累计 = Σ(postings WHERE date < D)（C-01 日初，不含 D 当日）
          差额 = target_balance − 当前累计
  → 展示「当前累计 / 目标 / 将自动补记 ±差额」+ 若 D 之后有交易则二次确认提示
  → 生成一笔普通 * 交易（差额分录 + Equity:Opening-Balances 对手分录），日期 = D-1【主理人裁定 2】
           且必须 >= max(账户 open_date, 账本期初日期)；区间为空 → 可读错误，不静默取更早日期
           UI 文案统一「截至 D 日初（前一日日终）」
  → 写 balance_date / balance_key（015 独立列，不写 opening_account_uuid）+ sync_log op=create
  → 同一 (账户, D) 再次设置 → 冲正旧校准 + 新建校准（版本递增），不覆盖
```

**流程 C · 导入（含 pad/balance 分支）**

```
选择 target=current（默认）或 target=new
  → 只读预检：严格子集解析 + 逐笔借贷平衡校验 + 冲突清单 + 差额重算
      ├─ 含 pad/balance 且 target=current → 整体拒绝 import_pad_balance_unsupported
      │    逐条列出 行号/类型/账户/目标金额/按当前账本重算的差额 + 两条出路文案
      ├─ 含 pad/balance 且 target=new → 按 C-02 展开成普通 * 交易 / 导入后自检
      └─ 不支持语法（除上述）→ 整体拒绝并列全部错误行号
  → 执行：单一大事务
      同名账户按 name 复用（类型/已关闭冲突整体拒绝）
      每笔交易：client_request_id = "import:"+sha256(规范化交易文本)
                txnID, inserted, err := insertTransactionRowTx(...)
                if !inserted { skipped++; continue }   ← 必须修复，否则 txnID=0 插 postings 导致整事务回滚
      逐笔借贷平衡校验通过才落库；写 sync_log op=create + import_batch_id
  → 结果：{新增/跳过/复用/新增币种} 计数 + 可「撤销本次导入」（按 import_batch_id 单事务回滚本次新建实体）
```

**流程 D · 修改交易**

```
在线打开交易详情（数据来自 GET /api/transactions 的 TransactionView）
  → can_edit?: boolean 决定「修改」入口可用 / 禁用（服务端计算须包含 D-15 判定）
      ├─ 原交易 reversed_by 非空（已冲正）→ can_edit=false，入口禁用
      │    固定文案「该交易已被冲正，请修改最新版本」（不复用「修改需联网」）
      │    （【2026-11-14 老板裁定修订】砍掉版本链：无「前往最新版本」跳转入口）
      │    直接 PATCH → 409 txn_already_reversed（不带 latest_uuid，客户端刷新流水自行定位改后交易）
      ├─ 在线失败 / 离线 → 按钮保留位置、置禁用 + 固定文案「修改需联网」；不按 navigator.onLine 显隐
      └─ 可用（改后交易为普通交易，可续改）→ 提交 PATCH（携带改后 date/flag/description/tags/postings）
            → 服务端独立校验 requireOwner || created_by == uid（防绕过）+ D-15 已冲正判定
            → 单一事务（【主理人裁定 1】原交易保留不软删）：
               ① UPDATE transactions SET reversed_by=<冲正 uuid> 标记原交易「已冲正」→ sync_log op=update
               ② 新建冲正交易（分录取负、reversal_of=原 uuid）→ sync_log op=create
               ③ 新建改后交易（新 uuid）→ sync_log op=create
            → 三者净效果 = 改后交易；写 edit_key 幂等（禁止复用 client_request_id）
            → 再次编辑该「改后交易」时重复上述三步（【2026-11-14 老板裁定修订】砍掉版本链：
               不形成 v1→v2→v3 展示链，改后交易作为普通交易存在于流水中）
  → ~~详情页展示 v1→v2→v3 全版本时间线~~（已裁剪）；仅保留「已冲正/冲正」徽章
    （原交易仍在流水中、不进回收站）
  → 导出仍为纯普通交易（原 + 冲正 + 改后三笔均在 deleted_at IS NULL 内）并过 bean-check
```
